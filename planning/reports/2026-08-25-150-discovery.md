## 0. The short version

Four premises the 2026-07-20 design carried are **falsified or superseded at HEAD**, and
they cut in opposite directions:

| # | Premise as filed | State at HEAD | Direction |
|---|---|---|---|
| 1 | FM tools need compile-time `@Generable` args, so MCP's runtime JSON schemas cannot bridge (the "central OPEN QUESTION") | **FALSE — and it always was.** Runtime schemas are fully expressible; typecheck-proven tonight | **FOR** |
| 2 | The host cannot call phone-local tools; that transport "does not exist" (the "tier inversion") | **FALSE.** It shipped — `talaria_phone_query`, a synchronous 40 s round trip, live on both ends | **AGAINST the doc's tier story** |
| 3 | Hermes-side MCP is not in the picture | **FALSE.** Hermes ships a mature MCP client (stdio + streamable HTTP + SSE + OAuth 2.1) with a deferred registry | **AGAINST** |
| 4 | Free-tier model-driven MCP fits the on-device budget | **FALSE on 4096-token hardware** — the doc's own budget omitted the resident device belt | **AGAINST** |

And one **new risk** that did not exist at filing: #346 measured what happens when two tool
surfaces coexist on one agent — the model picked the legacy MCP tool by name-literalness and
bypassed the on-device privacy gates. App-side MCP would make a **third** surface with
name collisions by construction (§2.3).

**Net:** the *mechanism* is easier than we thought; the *value* is narrower than we
thought. The marquee framing ("game changer") is weaker for Connected and blocked by
arithmetic for Free. What survives is a real but niche slice — plus a namespacing problem
the design doc does not yet address.

## 1. What the ruling asked, answered point by point

The 08-09 ruling named four things to test the fit against.

### 1.1 The shipped `CapabilityRegistry` (#284 stages 1–2) — SHIPPED, and it has an MCP-shaped hole

`Talaria/Services/Live/DeviceTools/CapabilityRegistry.swift` ships and is consumed in
production (`ChatScreen.swift:274` `/capabilities` sheet; `LocalChatBackend.swift:1641,2315`
for the armed-persona blurb). Its source enum is already:

```swift
enum CapabilitySource: String, Sendable { case device; case hermes, mcp, skill }
```

`.mcp` is **declared and unpopulated** — 15/15 live descriptors are `.device`. The registry
is built structurally (`init(belt: [Any])` filters for `CapabilityDescribing` conformance),
so an MCP tool that conformed would appear in the capabilities sheet and the armed blurb
with **zero registry changes**. That is a genuine fit improvement over filing date: the
seam #150 needs was built for another lane and is sitting empty.

**And it was built partly *for* #150.** #284's own entry names this scenario as the payoff:
a broker exists because "50+ capabilities would exceed the entire 8k window… the broker
decouples capability COUNT from context COST." The decoupling half, however, is exactly
what did not ship (§1.3) — what shipped is the *descriptor* half. Worth being precise
about, because the entry reads as if the cost problem were solved.

### 1.2 The measured `fullBelt=1648tok` budget — and the arithmetic that decides Lane C

`1648` is a **captured device measurement**, not a code constant (2026-08-09, 15-tool belt,
`dispatch/DEVICE-PASS-RUNNING-LIST.md:182-189`). In code the number is always live-measured
via `SystemLanguageModel.tokenCount(for:)` in `LocalChatBackend.flushSessionBudgetMeasurements()`
(`LocalChatBackend.swift:1281-1339`). Mean ≈ **110 tok/tool** across 15 tools.

**The design doc's §6 budget omitted the device belt entirely.** It budgeted the MCP tool's
schema (≤300 tok) and its result (≤1500 tok) against a "4096/8192 TOTAL" window, and never
subtracted the belt already resident on every armed turn, nor the response reserve.
Production reserves **1024** tokens for the answer on-device
(`LocalChatBackend.responseHeadroomTokens(for:) → 1024`, `.privateCloud → 4096`), so the
usable prompt-side budget is `contextSize − 1024`:

| | 4096 window | 8192 window |
|---|---|---|
| Usable prompt-side budget | 3072 | 7168 |
| Device belt (measured) | 1648 (**53.6%**) | 1648 (23.0%) |
| + one MCP tool schema (doc's ≤300) | 1948 (63.4%) | 1948 (27.2%) |
| + one MCP result (doc's ≤1500) | **3448 — EXCEEDS 3072** | 3448 (48.1%) |
| Left for instructions + transcript + prompt | **negative** | ~3720 |

**Finding: at the design doc's own budgets, free-tier model-driven MCP does not fit a
4096-token device at all**, and is comfortable only on 8192-class hardware. This is not a
tuning problem — the belt alone is over half the usable window before MCP arrives.

Two escapes exist, and both are other people's lanes:
- **Narrow the belt when an MCP tool is armed** — i.e. selective arming, which did not
  ship (§1.3).
- **Defer the schemas** — Hermes's own answer (§2.3). Costs 3 model round trips per cold
  call, which the record correction's "no planning, no chaining" ceiling and the shipped
  `ToolCallGovernor` (12 calls/turn, 4/tool) make a poor bet on a 3B model.

### 1.3 Selective arming's 4.76% danger-bar failure — Lane C's hard dependency

#284's vector probe (run `0AF5A6D8`, build 2225, errors=0, zero variance) **MISSED** the
pre-registered ≤2% dangerous bar at **4.76%** (5/105), and the in-scope exact-set bar at
37.5% (30/80). Per its own pre-registration, **selective arming did not ship**;
`ToolIntentRouteVector` / `routeVector` remain `#if DEBUG` in
`LocalChatBackend+IntentRouting.swift:431,547-603`, with a doc comment promising a
promotion commit that has not happened.

Production routing is therefore still **binary**: `routeTurn` → `turnRoutedToolless`, and
`effectiveOfferedTools` returns either `[]` or the **whole 15-tool belt** (minus vision
without an image, the only per-turn narrowing that ships). **There is no mechanism today
to arm an MCP tool only on turns that need it** — it would ride every armed turn at full
schema cost.

Two nuances worth carrying, because they change what the failure means for #150:
- The danger bar measures **narrowing** (a narrowed belt missing a tool production would
  have used). MCP is **addition**, not removal — so the 4.76% figure is not directly a
  risk to an MCP tool; it is the reason the *fix* for §1.2's arithmetic is unavailable.
- Every in-scope miss was a **superset** — the router over-arms and never under-arms
  (DANGEROUS=0 on all 16 in-scope rows). A superset-tolerant arming design was explicitly
  filed as **NEW work with NEW bars**, not a reopening.

### 1.4 "Does a Hermes-brain-only scope change the context math?" — YES, decisively, and against us

If the scope is Hermes-brain-only, the phone's 4096/8192 window is **not the constraint at
all** — the host's is, and the host has already solved this problem twice over:

1. **Hermes ships a full MCP client.** `tools/mcp_tool.py` (~8.6k lines, checkout head
   `beb794123618`, `hermes-agent 0.20.5`) connects over **stdio, Streamable HTTP, and SSE**,
   with OAuth 2.1 PKCE, mTLS, and protocol-version negotiation. Transport selection is
   literally `transport_type = "HTTP" if "url" in config else "stdio"` (`mcp_tool.py:7560`).
   Config is `~/.hermes/config.yaml` → `mcp_servers:` with `url`/`headers`.
2. **It already solves the many-tools context problem** with the deferred registry
   (`tools/tool_search.py`): MCP and non-core plugin tools are replaced in the model-visible
   array by three bridge tools — `tool_search` / `tool_describe` / `tool_call` — with a
   tiered embedded listing gated at ~4000 listing tokens / 5% of context.

**Consequence:** for any MCP server the *host* can reach, a Connected-tier Talaria user
already has that capability today, through Hermes, with no app change. Building an app-side
MCP client to serve Connected duplicates a shipped, better-resourced implementation.

The residue — and it is the only genuinely unique slice — is **servers the host cannot
reach but the phone can**: something on the phone's own network position (a work/lab
network, a captive LAN, a peer device) or running on the phone itself.

## 2. What else changed since filing (verified at HEAD)

### 2.1 The FM↔MCP impedance problem is solved by the framework — MEASURED tonight

The design doc's §6 called this "the central OPEN QUESTION" and recommended a **curated
single-`query: String` shape** as v1 because MCP tool schemas are runtime JSON while FM
tools take compile-time `@Generable` arguments. **That constraint does not exist.**

From the beta6 iOS SDK interface on disk
(`.../Xcode-beta6.app/.../iPhoneOS.sdk/.../FoundationModels.swiftinterface`):

```swift
public protocol Tool<Arguments, Output> : Sendable {
  associatedtype Arguments : ConvertibleFromGeneratedContent   // NOT Generable
  var parameters: GenerationSchema { get }                     // a REQUIREMENT
  ...
}
extension Tool where Self.Arguments : Generable { public var parameters: GenerationSchema { get } }
```

`parameters` is a protocol requirement whose default lives only in a constrained extension,
so a concrete type may supply its own — built at **runtime** via
`GenerationSchema.init(root: DynamicGenerationSchema, dependencies:) throws` (iOS 26.0+).
`GeneratedContent` conforms to `Generable`, carries `init(json:)` and `.jsonString`, and
reads fields via `value(_:forProperty:)` — i.e. it is exactly the open box an MCP
`tools/call` argument payload needs.

**Measurement, not inference.** A probe declaring
`struct RuntimeSchemaMCPTool: Tool { typealias Arguments = GeneratedContent; let parameters: GenerationSchema }`,
building an object schema (string + optional int + `anyOf:[String]` enum) at runtime and
handing the tool to `LanguageModelSession(tools:)`:

```
TYPECHECK_EXIT=0
MARKER: RUNTIME_SCHEMA_TOOL_TYPECHECKS_CLEAN
```
(`swiftc -typecheck -target arm64-apple-ios27.0`, Xcode-beta6 iPhoneOS27.0 SDK.)
**Negative control** (deliberately bad annotation on `GeneratedContent.generationSchema`)
returned **2 errors**, proving the compiler resolved the real framework rather than passing
vacuously. Probe preserved at the session scratchpad; it is ~60 lines and trivially
re-creatable.

**Consequences:** the doc's option 1 (curated single string) is unnecessarily narrow;
option 2's mechanism was misidentified (it is `DynamicGenerationSchema`, not "Dynamic
Profiles"); option 3 (JSON-string passthrough) stays correctly rejected. A faithful MCP
tool bridge — full argument schema, guided generation intact — is available and has been
since iOS 26.0. **This removes the mechanical blocker on Lane C. It does not remove the
budget blocker in §1.2, and it grants the 3B model no planning.**

### 2.2 The "tier inversion" is superseded — the host↔phone transport SHIPPED

The doc's §5 said the host→phone tool transport "does not exist… it becomes its own
post-1.1 design doc (Lane D placeholder)". It exists, on both ends, at HEAD:

- **Host half** — talaria plugin `0.5.0` (`~/.hermes/plugins/talaria`, head `e6695495`)
  registers exactly one agent tool, `talaria_phone_query` (`talaria/tools.py:29-54`), a
  multiplexed `kind` enum over `location | health | motion | weather | calendar |
  reminders | deviceStatus`. `TransportHub.enqueue_query` parks an `asyncio.Future`, the
  phone's long-polled `drain` (25 s hold) carries the query down, the phone POSTs
  `query_result` back, and the tool returns **inside the same model turn**
  (`_QUERY_TIMEOUT = 40.0`).
- **Phone half** — `Talaria/Services/Live/TalariaPlatformLink.swift` (drain / ack /
  answer) and `Talaria/Services/Live/PhoneQueryResponder.swift`, which dispatches the same
  seven kinds onto the device belt's readers behind the sensor gates.

So the naive tier story is restored, not inverted: **the host model already reaches
phone-local capability.** What it reaches is a **hardcoded, hand-synced 7-kind enum** —
`PhoneQueryResponder.answer(kind:params:)` is a literal switch whose own comment warns that
it and the gate switch "are two hand-synced lists". Adding a capability means editing the
plugin, editing the app, and shipping a build.

**This is the strongest surviving argument for #150, and it is a different argument than
the one filed:** an MCP client on the phone would give that *existing* channel a **dynamic**
capability surface — the phone advertises N discovered tools, the host calls them by name —
instead of a static enum that costs an App Store release per capability.

### 2.3 Other state deltas that bear on the entry

- **Relay retired on both hosts** (#375). The doc's Lane D sketch — "host agent → relay →
  phone executes → result back" — names a component that no longer exists. The surviving
  path is the plugin's platform-events envelope, which is better.
- **Runs plane is the only chat transport** (#382/#368). Note the runs SSE stream drops
  tool `args`, which is precisely why the artifact mirror exists (#362) — and why any
  future phone-side tool surfacing must ride the plugin channel, not the run stream.
- **No tool-result injection into a running run.** `/v1/runs/{id}/approval` takes a
  choice; `/v1/runs/{id}/steer` takes free text; there is **no** structured tool-result
  endpoint. The plugin's `query_result` verb is the only place an external client supplies
  a genuine tool result, and it resolves in-process, entirely outside the runs machinery.
- **Talaria's own host tool is deferrable** under Hermes's rule (`toolset="talaria"` is
  neither core nor `mcp-*`), which is a live cross-ref for #347's scoring discipline.
- **A shipped precedent for MCP approval UX on the phone:** #304's typed approval card
  already handles the host's **`pattern_key: "mcp_elicitation"`** shape over
  `POST /v1/runs/{id}/approval`. Whatever #150 does for consent, the visual and interaction
  language exists. *(Flag for Owen, not asserted: #251's live entry still records "every
  MCP elicitation AUTO-DECLINES on the chat plane" as an open HITL gap — that note predates
  #304's card and may be stale. Not verified in this pass; it needs its own look rather
  than a correction written blind from here.)*
- **🔴 THE STRONGEST RISK ARGUMENT AGAINST, and it is empirical (#346).** Running two tool
  surfaces on one agent has already bitten this project: the legacy `hermes_mobile` MCP
  toolset **shadowed** the talaria plugin, and the model silently picked the legacy MCP tool
  **by name-literalness** — bypassing the on-device privacy gates and the honest-unreachable
  prose. An app-side MCP client would add a **third** capability surface alongside the device
  belt and the host's plugin tool, with overlapping names by construction (a user's MCP
  server may well expose `get_location` or `read_calendar`). #346 is the measured precedent
  that this is not a theoretical concern, and any #150 build must carry a
  namespacing/precedence design that #150's current doc does not have.
- **Nothing of #150 has been built.** No `Package.swift`; `project.yml`'s `packages:` block
  still contains only WebRTC 130.0.0; zero `*MCP*` files under `Talaria/`. The one hit is a
  cosmetic `SlashCommand(name: "reload-mcp", …, isLocal: false)` — a *Hermes* command label
  passed to the host, not app-side MCP.
- **`design/MCP_CLIENT_DESIGN.md` §1 cites `IOS27_NATIVE_CAPABILITIES.md`, which does not
  exist** in this repo and never has (`git log --all -- '*IOS27*'` is empty). The context
  numbers it attributes to that file are nonetheless correct against code
  (`LocalChatBackend.swift:15-16`).
- **The SDK verdict is UNVERIFIED tonight.** `modelcontextprotocol/swift-sdk` `from: 0.11.0`
  was verified 2026-07-20 and not re-checked — no network by scope, and no local SwiftPM
  cache copy exists. Locally corroborated only that the current spec revision is
  **2025-11-25** (from `mcp` 1.28.1 in the HermesMCP venv), matching the doc's claim.
  Lane A's compile gate (iOS minimum × Swift 6 region isolation) remains genuinely open.

## 3. Options for Owen

Costs are relative; none of these is launch-pass work under #150's own scope.

**Option 1 — CORRECT THE RECORD, STAY PARKED.** Docs-only: rewrite
`design/MCP_CLIENT_DESIGN.md` §5 and §6 against §2.1/§2.2 above, add the §1.2 arithmetic,
retire the "curated single string" recommendation, and add the §2.3 namespacing/precedence
question #346 forces. #150 stays post-launch, unbuilt.
*Cost: one small docs lane. Risk: none. Leaves the item honest for whoever picks it up.*

**Option 2 — NARROW TO A MANUAL CONSOLE (Lanes A + B only, never C).** Server registry +
Keychain creds + honest probe + browse tools + manual invoke through
`ToolConfirmationCenter` + insert result into chat as quoted context. **Sidesteps §1.2
entirely**, because a manually invoked result enters as *text* and no schema ever joins the
belt. Serves both tiers. *Cost: two medium lanes + an SPM dependency. Value: real but
niche.*

**Option 3 — INVERT: make the EXISTING host→phone channel dynamic.** Keep the phone as an
MCP client, but the consumer is the **host** model via `talaria_phone_query` (a new `kind`,
or a sibling verb carrying tool name + args). This is the closest thing to the original
"game changer", and §2.2 makes it far cheaper than the doc's Lane D imagined. *Cost: app +
plugin, two-sided. Caveat: only pays off for servers the host cannot reach itself, since
Hermes's own MCP client covers everything else.*

**Option 4 — KILL as considered-and-declined (re-filable), per tonight's #253 precedent.**
Argue: Connected is served by Hermes's shipped MCP client; Free is blocked by arithmetic
until selective arming ships; the unique slice is too narrow for a 1.1 marquee. Retire the
design doc and both dispatch specs with a dated pointer.
*Cost: one tracker commit. Risk: discards a genuinely-improved fit (§1.1, §2.1).*

### Recommendation

**Option 1 now; hold the build question until after launch, and if it is ever built, build
Option 2's shape — not Lane C.**

Reasoning: the discovery the ruling ordered has changed the *facts* materially, so the
cheapest correct move is to stop the two dead premises from being inherited. Option 4 is
premature — #150's fit genuinely *improved* on the two mechanical axes (§1.1's empty `.mcp`
seam, §2.1's runtime-schema bridge), and killing it tonight would discard that on the
strength of a value argument that only bites in the Connected tier. Option 3 is the most
interesting and should be **named in the entry as the real form of the original ambition**,
but it is two-sided work whose payoff depends on a slice we have not sized.

**Lane C (model-driven on-device MCP) should be treated as dead on 4096-token hardware
until selective arming ships**, and any revival must re-derive §1.2's table against the
belt cost measured on that day — not against the doc's belt-free budget.

### What is explicitly NOT recommended
- Do not adopt the SPM dependency before Lane A's compile gate is a real decision — the
  iOS-minimum × Swift-6 question is still open, and the toolchain has moved twice since
  the verdict was written.
- Do not build a phone-side deferred-tool registry to buy back context: three model round
  trips per cold call is a bad bet against the record correction's ceiling and the shipped
  governor's caps.
