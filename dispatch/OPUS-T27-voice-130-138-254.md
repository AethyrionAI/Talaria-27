## 2. Verified state — who owns the audio session, and who owns the session's life

### VERIFIED (read at HEAD `35c6234`)

**Teardown has TWO owners and neither is a service.**

1. **`VoiceOverlayScreen.onDisappear`** — `Talaria/Features/Talk/VoiceOverlayScreen.swift:91-110`.
   A **view** owns the dismissal teardown. It sleeps 500 ms, re-checks
   `showLiveCameraOverlay`, then calls `talkStore.abandonSession()`. Deliberately
   **unguarded** — the #139 comment in place says so: *"NO `isSessionActive` guard.
   That guard is why dismissal during a slow connect tore nothing down."*
2. **The #118 background observer** — `Talaria/Stores/AppContainer.swift:1148-1161`.
   Fires on `UIApplication.didEnterBackgroundNotification`, and it **is guarded**:
   `TalkBackgroundRule.shouldEndSession(isSessionActive:routeHasCarAudio:)`.

**The guard is the one #139 removed from the other path, still in place here.**
`Talaria/Services/Support/TalkSessionRules.swift:32-34`:

```swift
static func shouldEndSession(isSessionActive: Bool, routeHasCarAudio: Bool) -> Bool {
    isSessionActive && !routeHasCarAudio
}
```

**`isSessionActive` is FALSE for the whole connect window.**
`TalkStore.startSessionDirectly()` (`Talaria/Stores/TalkStore.swift:80-99`) sets
`connectionState = .connecting` synchronously, then `await voiceService.startSession()`,
and only afterwards does `applySnapshot` flip `isSessionActive`. So between the
`.task` firing and the connect returning, `shouldEndSession` returns **false** and
the background observer does **nothing**.

**`abandonSession` is the unguarded revoke, and the background path does not use
it.** `Talaria/Stores/TalkStore.swift:110-113` bumps `sessionGeneration` first;
`AppContainer.swift:1159` calls the guarded `endSession()` instead, and only after
clearing the guard.

**The audio that would be heard is forced to the loudspeaker, by us, on purpose.**
`LiveVoiceSessionService.configureAudioSession()` —
`Talaria/Services/Live/LiveVoiceSessionService.swift:745-765` — sets
`.playAndRecord` + `.voiceChat` + `.defaultToSpeaker`, then, when no headphones /
Bluetooth / CarPlay output is present, `overrideOutputAudioPort(.speaker)` with the
in-source comment *"for maximum volume."* `forceSpeakerIfNeeded()` (`:770-786`)
re-asserts it. **"Started talking to me full volume" is this line, not a mystery.**

**The realtime engine survives backgrounding by declaration.** `project.yml:353-357`
lists `UIBackgroundModes: [fetch, processing, location, audio]` — verified in the
manifest, not inferred from the comment at `TalkSessionRules.swift:29-31`.

**#138's stated mechanism is FALSIFIED by source. Both owed discriminators are
answered, and neither needed a phone.** #138 asks (`OPEN_ITEMS.md:3148-3160`)
whether the realtime path speaks via the app's own TTS, or extracts the remote PCM
and renders it itself — either of which would leave WebRTC's AEC with no far-end
reference.

- **It does not use app TTS.** `grep speechOutput|SpeechOutputService` over
  `LiveVoiceSessionService.swift` returns **zero** matches. The same grep over
  `NativeVoicePipelineService.swift` returns ten (`:83`, `:128`, `:281`, `:284`,
  `:396`, `:420`, `:475`, `:511`, …). The app TTS belongs to the **native** engine
  only.
- **It does not touch the remote track.**
  `peerConnection(_:didAdd stream:)` is an empty body —
  `LiveVoiceSessionService.swift:1327`. The only `RTCAudioTrack` the app holds
  (`:153`) is the **local** mic track it creates and adds
  (`:939-940`, `trackId: "hermes-mobile-audio"`). No PCM extraction, no custom
  renderer. **WebRTC's own audio device module plays the downlink, so the AEC has
  its far-end reference by construction.**

**What IS anomalous in the realtime audio path — the surviving mechanism family:**
**the app never uses `RTCAudioSession`.** `grep -r "RTCAudioSession\|useManualAudio"`
over `Talaria/` returns **nothing**. Every configuration goes to
`AVAudioSession.sharedInstance()` directly, outside WebRTC's coordination object,
while WebRTC's ADM is live. The codebase already documents the resulting fight —
`LiveVoiceSessionService.swift:980`: *"…internally, which can reset our
`overrideOutputAudioPort(.speaker)`."*

**#198B's fault is still reachable, and there are two classes of site.**
`AudioSessionOffMain` (`Talaria/Services/Support/TalkSessionRules.swift:119-141`)
is a `Task.detached` shim; four call sites use it
(`LiveVoiceSessionService.swift:353,687,746`, `NativeVoicePipelineService.swift:399`).
**Synchronous `AVAudioSession` calls remain inside `@MainActor` classes:**

- `Talaria/Services/Live/NativeVoicePipelineService.swift:951-957` — `setActive(false)`
  → `setCategory` → `setActive(true)`, inside `LiveSpeechService.start(muted:)`'s
  caller chain on a `@MainActor` type (`:23-24`).
- `Talaria/Services/Live/LiveSpeechService.swift:230-231` — `setCategory` +
  `setActive(true)`, class is `@MainActor` (`:12-14`).
- `Talaria/Services/Live/SpeechOutputService.swift:248-249,264` — **deliberate**,
  with a written rationale at `:236-243` (activation must complete before `speak`
  on the same tick).

**The native RESUMPTION path — where #198B's fault fired — reaches the first of
those.** `NativeVoicePipelineService.swift:769-782` (resumption observer) →
`handleInterruptionEnded` (`:805-812`) → `restartCapture()` (`:335`) → capture
restart → the synchronous block at `:951-957`.

**The iOS 27 async API the fault message recommends EXISTS, and I verified it with
the compiler rather than assuming it does not.** Beta4 SDK header
`…/iPhoneOS.sdk/System/Library/Frameworks/AVFAudio.framework/Headers/AVAudioSession.h:278`
declares `activateWithOptions:completionHandler:` `API_AVAILABLE(ios(27.0))` and
`:287-289` declares `deactivateWithOptions:completionHandler:`. Swift spelling
confirmed by `swiftc -typecheck -target arm64-apple-ios27.0` using the
`let x: Int = …` signature-printing trick:

```
error: cannot convert value of type 'Bool' to specified type 'Int'
   let x: Int = try await s.activate(options: [])     // ⇒ async throws -> Bool
   let y: Int = try await s.deactivate(options: [])   // ⇒ async throws -> Bool
```

**So `AudioSessionOffMain`'s `Task.detached` is a workaround for an API that now
exists.** Not a platform limit. (Standing lesson: "no API exists" has been wrong
3/3 on this project.)

## 4. Shared fix or three fixes — the verdict

**Three items, TWO lanes, ONE shared file, and no umbrella.**

- **#130 is not a lane.** It is closed. Its only remaining artifact is tracker
  hygiene plus the parked §B1 reminder. **Do not open work on it.**
- **#254 and #138 share a FILE — `LiveVoiceSessionService.swift` — and share an
  INSTRUMENT (the engine-pin log line). They do not share a fix**, and the
  evidence for that is specific:
  - #254's defect is **ownership**: nothing revokes a session whose start is
    in flight when the app leaves the foreground. The fix is in
    `TalkSessionRules.swift` + `AppContainer.swift` + `TalkStore.swift`, is
    **engine-independent**, and touches no audio code at all.
  - #138's defect is **acoustic/routing**: the uplink carries the assistant's own
    audio back to the server VAD. The fix is in the realtime audio session
    configuration or at the uplink gate, is **realtime-only**, and touches no
    lifecycle code.
  - The only genuine coupling is cosmetic: the *loudness* of #254's ghost comes
    from the same `overrideOutputAudioPort(.speaker)` line that bar 138-D
    interrogates. **A shared line of code is not a shared fix.** Ending the ghost
    session does not improve echo cancellation, and fixing echo cancellation does
    not end a ghost session.

**So: do not manufacture a voice umbrella.** Two independent lanes, run in either
order. If one must go first, **#254**, because its fix is off-device and its bars
are unit-testable, while #138's decisive bars need a phone.

**One file, deliberately.** Splitting #254 into its own dispatch would force both
documents to restate §1's engine gate, the airplane-mode pin, the headphone pin,
and the #220 trap list — four duplications maintained in two places, which is the
"a check that lives in two places drifts" failure #58's own note warns about. The
lanes are separated by heading, not by file.

## 5. The #254 mechanism — named owner, named race

**The ownership bug, stated plainly: the voice session's lifetime is owned by a
SwiftUI view (`VoiceOverlayScreen`), with a guarded background observer as the
only backstop. No store or service holds the invariant "a session may not outlive
the foreground."**

The race, entirely from §2's verified lines:

1. Control Center "Talk to Hermes" → intent sets `isVoiceOverlayPresented`
   (`Shared/HermesControlIntents.swift:148` → `DeeplinkRouter.swift:47-52`, or
   `StartVoiceSessionIntent.swift:28`). Cold launch: the **slowest possible**
   connect — this path is why Owen's report is the first sighting.
2. `VoiceOverlayScreen.task` → `startSessionDirectly()`. `isSessionActive` is
   **false** for the whole connect (`TalkStore.swift:80-99`).
3. User leaves the app before the connect returns. `onDisappear` does **not** fire
   (ASSUMED — Task 1 verifies). The #118 observer fires, evaluates
   `shouldEndSession(isSessionActive: false, …)` → **false**, and returns without
   touching anything (`AppContainer.swift:1154-1158`).
4. The connect lands. `applySnapshot` flips `isSessionActive` **in the background**.
   `UIBackgroundModes: audio` (`project.yml:353-357`) keeps WebRTC streaming, and
   `configureAudioSession` has already forced the loudspeaker
   (`LiveVoiceSessionService.swift:757-762`).
5. **A live, speaking, full-volume session with no UI and no owner.**

Every step is a verified line except step 3's `onDisappear` assumption. **The fix
is to give the background path the same unguarded revoke the dismissal path got in
#139** — with one caution, below.

**Do NOT simply delete `isSessionActive` from the rule.** Firing
`abandonSession()` on *every* backgrounding would call `endSession()` with no
session live, and `endSession` reaches
`AudioSessionOffMain.setActive(false, .notifyOthersOnDeactivation)`
unconditionally (`LiveVoiceSessionService.swift:353`,
`NativeVoicePipelineService.swift:399`). `AppContainer.swift:1268-1276` records
what that class of stray deactivation already cost once (#84: *"each stop() used
to reach setActive(false) on the shared session, killing the live mic"*). **The
rule needs a third input — "a start is in flight" — not the removal of its first.**
`TalkStore` has the fact privately (`sessionGeneration`, `:53`) but publishes no
`isStartingSession`.
