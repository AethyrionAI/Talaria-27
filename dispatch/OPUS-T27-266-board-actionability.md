## Task breakdown

### Task 1 — the triage sweep (THE PARALLELIZABLE PREREQUISITE)

**~104 unclassified live items, in batches of 20.** This is the only job in
the current queue that fans out cleanly, and it is most of the lane's cost.

Per batch, the classifier:
1. Reads each item **in full — not the header.** The board's own standing
   warning applies: *"Do not read a header and stop. Every header-only
   judgement made during this phase was wrong… Six items looked closable
   from their headers; zero were."*
2. Cross-checks `dispatch/DEVICE-PASS-RUNNING-LIST.md` before assigning
   ACTIONABLE — a device-debt item is not actionable at a keyboard.
3. Returns a table: item · bucket · one-line justification · any residue
   found that contradicts the item's own header.
4. **Flags, does not fix.** A classifier that starts correcting entries is a
   classifier whose batch cannot be reviewed.

Batches are independent; run them concurrently. Have each return structured
output so the results merge without hand-editing.

### Task 2 — reconcile and adjudicate

Merge the batch tables. Expect disagreements at the ACTIONABLE /
DEVICE-DEBT / WATCH boundaries — resolve them against the device list and
the item bodies, and record each resolution. **Anything genuinely ambiguous
goes to Owen as a list, not as a guess.**

### Task 3 — regroup, verbatim

Move blocks under status headers. **Move, never edit.** Add the per-item
bucket marker required by 266-E in the one place it can live without
touching the body — decide where (a line immediately under the header is the
obvious candidate) and apply it uniformly.

Run the 266-B byte-identity check **before** committing, not after.

### Task 4 — regenerate the INDEX, and kill the stale counts

The INDEX becomes section-grouped. Its footer count is generated. Then
correct the stale figures **at their own homes** (266-D): the INDEX footer,
#266's own "~100" prerequisite line, and any handoff that carries 118.

### Task 5 — the verifier

Write the checks as **runnable commands**, in the #261 style, and paste their
output into the close-out commit. Do not reach for
`scripts/oi-split-verify.py` — it is a **one-shot proof of a historical
commit range**, pinned to `8077ecb` → `af59ea7`, and it does not read the
working tree. Running it and seeing green proves nothing about this sweep.
*(If the archive-pass lane adds a live mode to that script, reuse it here —
check whether it did before writing your own.)*

### Task 6 — commit and close out

One commit, message naming the bucket counts before/after and carrying the
verifier output.

## Traps

- **The "tidy while we're in here" trap.** A regroup touches every block in
  the file. Every fix made in passing defeats 266-B and makes the diff
  unreviewable. **Corrections are a separate commit, after the regroup, with
  their own justification.**
- **A header is not a status.** See the board's own six-for-six warning.
- **DEVICE-DEBT vs ACTIONABLE is where the value is.** Get this boundary
  wrong and the lane produces a differently-shaped overstatement.
- **The count has been wrong four different ways.** Do not add a fifth by
  hand-writing one. Generate it.
- **Numbering is untouchable.** Nothing is renumbered, ever, in either file
  (#261). A regroup that reorders blocks is fine; a regroup that renumbers
  is a catastrophe.
- **This lane will surface closable items the archive pass missed.** File
  them; do not sweep them in this commit. Two verbatim-move operations in one
  diff cannot be verified separately.
