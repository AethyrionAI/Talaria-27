# #137 Sensor Opt-In Redesign Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Kill the post-pair permissions wall; sensor streaming becomes a Settings-level master opt-in (OFF by default) with contextual per-sensor grants, grandfathering devices that already stream.

**Architecture:** A new `sensorStreamingEnabled` master flag (plus a new `motionCollectionEnabled` per-sensor gate) in `UserSettings` gates `SensorUploadService.start()` via an injected closure — one seam covers every start call site, and the check is an in-memory read (#136-safe). Grandfathering is a one-shot migration keyed on an **active pairing** (the pre-#137 consent gate), deferred while protected data is sealed. The post-pair `PermissionsOnboardingScreen` root-swap is removed entirely (sole call site: `AppRootView`); the #71/#31 `router.popToRoot()` in `ConnectHermesScreen.completePairing` already lands a successful pair in chat.

**Tech Stack:** SwiftUI, `@Observable`, Swift Testing (`@Test`), XCUITest, xcodegen, Xcode-beta4 (`DEVELOPER_DIR=/Applications/Xcode-beta4.app/Contents/Developer`).

## Global Constraints

- Branch: `claude/fable-t27-137-sensor-optin` off current main.

- Never assert HealthKit auth OUTCOMES in unit/UI tests (`CODE_SIGNING_ALLOWED=NO` strips entitlements — sim-verify-gotchas memory); test gating logic only. Unit tests must never enable the health gate on a constructed-and-started service (start() would fire a live `requestAuthorization` Task).
- HealthKit: check-before-request stands. `LiveLocationService.requestAuthorization` (guards on already-authorized), `LiveMotionService.requestAuthorization` (checks `CMMotionActivityManager.authorizationStatus`), and mic/speech guards already comply; health read-auth is unreadable by design and its request is silent after the first decision.

## Discovery record (for the PR description)

- **`PermissionsOnboardingScreen` call sites:** exactly one — `AppRootView.swift:22` (root swap on `pairingStore.needsPermissionsOnboarding`). It is NOT a Settings management surface; that role belongs to the separate `Features/Permissions/PermissionsScreen.swift` (routed via `Route.permissions` ← `hermes://health` deep link, `AppEntry.swift:340`) and `PrivacySettingsScreen`. → **Safe to delete the file.**
- **Grandfathering signal: active pairing** (`PairingStore.isPaired`, backed by the persisted `PairedRelayConfiguration`). Justification: every pre-#137 sensor start call site (`initialize()`, `handleSystemLaunch`, `handleBackgroundRefresh`, `handlePairingActivated`, `restartSensorPipelineIfPaired`) gates on `isPaired` and nothing else beyond the #6 revoke flags — pairing WAS the app-level sensor consent, and the permissions onboarding ran exactly at pair. Rejected alternatives: outbox history (a fully drained outbox is cleared from disk by design — unreliable negative), HealthKit grant state (read-auth unreadable by Apple design, in-memory only), `locationSyncPreference` (covers one sensor only).
- **The no-blob trap:** `SettingsStore` falls back to `DemoData.sampleUserSettings` when `loadUserSettings()` is nil. A paired device that never persisted settings would, after this lane flips fresh defaults to OFF, decode per-sensor gates as false → silent streaming stop. Migration therefore takes `hadPersistedSettings` and restores pre-#137 per-sensor defaults (true) when no blob existed.
- **Pre-first-unlock trap:** post-reboot background launches read pairing as absent (Keychain sealed). Migration must NOT stamp done then — gate on `UIApplication.shared.isProtectedDataAvailable` and re-run from the existing `refreshCredentialState` recovery closure (AppContainer.swift ~line 895).

  func setSensorStreamingEnabled(_ enabled: Bool) async {
